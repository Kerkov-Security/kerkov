# Kerkov

Security-focused conversational AI CLI for authorized penetration testing, security auditing, and CTF competitions. Integrates with LLM providers (Anthropic, Gemini, NVIDIA NIM, OpenRouter, DeepSeek, Ollama, Codex) to provide intelligent security analysis with tool execution capabilities.

## Conventions

- **Async everywhere**: All provider `complete()` and tool `execute()` methods are async. Use `asyncio`.
- **Abstract base classes**: Providers extend `BaseLLMProvider`, tools extend `BaseTool`.
- **Pydantic 2.0+** for data models, tool params (`{ToolName}Params`), and config.
- **Tool results**: All tools return `ToolResult(success, output, error, metadata)`.
- **Tool approval levels**: `NONE`, `OPTIONAL`, `REQUIRED` — respect per-tool settings.
- **Tool approval breadth**: every tool implements the abstract `approval_scope(params) -> ApprovalScope` (`core/approval_scope.py`), which says how far one approval may be generalized when the operator saves it as a rule — `exact_only()` (no broad rung), `whole_tool()` (`tool({})`), or a pattern from a boundary the tool's own arguments define (`matching`, `keeping`, `parent_directory`). `volatile` names params that never reach a saved rule: values the model varies per call (`timeout`) and payloads that would leak into the rules file (`write.content`, `http.headers`). It is abstract, not defaulted, so a new tool cannot inherit someone else's idea of "broad enough"; `tests/tools/approval_scope_coverage_test.py` enforces that.
- **Type hints required**: mypy strict mode is enabled. Use `Optional[T]` (not `T | None`) for Python 3.10 compat.
- **Formatting**: Black (line-length 88), isort (black profile). Run `black src/ tests/` before committing.
- **Blank lines (PEP 8)**: Two blank lines between top-level definitions (functions, classes); one blank line between methods inside a class. `black` enforces this — run it before committing.
- **Comments are sparse.** The code is expected to explain itself; write it so it does. Add a `#` comment only where something is genuinely non-obvious — a workaround, a non-local constraint, a subtle ordering requirement, a "why this and not the obvious thing". Never restate what the next line already says, and never narrate a block that reads fine on its own. If a comment feels needed to make code followable, prefer a clearer name or a smaller function.
- **Docstrings are one line.** A single summary line is the default for modules, classes, and functions. Expand past that only when a caller genuinely cannot use the thing correctly without it (a non-obvious contract, a surprising failure mode) — and then add the minimum, not a full Args/Returns treatment that duplicates the type hints. Multi-paragraph docstrings are rare and should feel earned.
- Known typo: `src/kerkov/providers/anthrophic_provider.py` — do not rename without coordinating.

## Tools (active suite)

`ToolSuite.get_tools()` always returns `ReadTool`, `ReadUrlTool`, `WriteTool`, `HTTPTool`, `ExecTool`, `ProcessTool`, `ContainerLifecycleTool`, `SbomGenerateTool`, `VulnerabilityScanTool`, `SastScanTool`, `CveLookupTool`, and `ZapTool`; it then appends `BrowserTool` (unless `include_browser=False`) and — when the selected search provider can run (Tavily → a saved/environment key or an interactive prompt; SearXNG → `SEARCH_BASE_URL`) — `WebSearchTool` (`web_search`). `KerkovCLI` then appends `SkillTool`, `RecallTool` and `LedgerTool` (both when `KB_ENABLED`), then a `SpawnAgentTool` (the `delegate` tool) and an `AgentWaitTool` (`agent_wait`). Notes:
- `HTTPTool` replaced the old `FetchTool`; supports GET/POST/PUT/PATCH/DELETE plus named credential profiles loaded from `config/http_profiles.yaml`.
- `WebSearchTool` is stage 1 (discovery) of a search→read loop: it returns snippet-level `title/url/snippet` results and is pluggable behind a `SearchBackend` ABC (`TavilyBackend` for the commercial Tavily API, `SearxngBackend` for a self-hosted SearXNG instance). Deep-read the promising URLs with `ReadUrlTool` (`read_url`). The SearXNG half is turnkey via `/searxng` (see below), the keyless alternative to a paid Tavily key.
- `ReadUrlTool` is stage 2 (reading): it fetches HTTP(S) HTML pages with `httpx` and extracts readable text and links locally with `trafilatura` (a required dependency); metadata `resolved_url` records the final URL after redirects. It needs no search provider or API key and is registered unconditionally. A 10 MB fetch guard limits downloads before extraction; `READ_MAX_CHARS` caps output including truncation markers. `max_chars` can request a smaller budget. Long pages return a head/tail preview; use the suggested `offset` or metadata `next_offset` to continue from the end of the head without skipping omitted content. The tail is a preview and can repeat across pages. `http` remains the tool for raw responses and API requests; JS rendering is outside `read_url`'s scope.
- `CveLookupTool` (`cve_lookup`) fuses NVD (CVSS/CWE/references), CISA-KEV (exploited in the wild), and EPSS (exploitation probability) into one `MergedCveRecord` with per-field provenance. The framework lives in `src/kerkov/core/intel/` (sources, merge, TTL cache) mirroring how `core/websearch/` backs `web_search`; the tool is a thin adapter. All sources are keyless so it is registered unconditionally.
- `ExecTool` runs one-shot or background commands via the process supervisor; backgrounded sessions are then driven through `ProcessTool` (`list`, `poll`, `log`, `write`, `send_keys`, `paste`, `submit`, `kill`).
- `SbomGenerateTool` (`sbom_generate`) creates Syft, CycloneDX, or SPDX JSON artifacts for workspace files or container images. `VulnerabilityScanTool` (`vulnerability_scan`) runs Grype against workspace directories, images, or an existing SBOM. Syft and Grype must be installed separately and available on `PATH`; Kerkov does not download or update them. Full reports/logs stay in the engagement workspace and compact normalized summaries go to the model.
- `SastScanTool` (`sast_scan`) runs an existing OpenGrep binary against explicit host-local targets and rule files, retains raw JSON/log artifacts in the engagement workspace, and returns a redacted bounded summary. Absolute paths are accepted; relative paths stay workspace-confined. Scans never install software; `kerkov setup opengrep` is the explicit setup path. Built-in agents do not receive it because their whitelisted calls bypass interactive approval.
- The legacy shell stack is gone: `ShellTool`, the `PersistentShell*` tools, their `core/shell/` backend, and the unreachable `/shell` handler were all deleted. Use `ExecTool` + `ProcessTool` for commands and ongoing sessions.
- `recall` (`RecallTool`) searches the engagement knowledge base — every tool result gathered so far, indexed by the ingestion hook in `conversation_engine`. Snippet-first like `web_search`; `full=true` or a query of `artifact#N` expands one record. Registered at CLI level (not in `ToolSuite`) because it needs a knowledge base keyed by the live `engagement_id`, which does not exist when tools are built — so it takes a getter rather than the store itself. Sits in the master tools snapshot, so an agent whose profile whitelists `recall` receives it — every built-in profile does; a user-defined `AGENT.md` has to name it in `allowed_tools` like any other tool.
- `ledger` (`LedgerTool`) writes to the findings ledger — the model's structured, always-in-context working memory (`assets/targets/connections/hosts/services/credentials/findings/flags/next_steps`). The tool exposes `op=add|list|remove|graph`; the web inventory also supports direct resource edits through `FindingsLedger.save_resource`. Registered next to `recall` — on the CLI and in the web console — and gated on the same `KB_ENABLED`; late-bound getters supply the `FindingsLedger` and the writing engagement id. `add` requires the section's identity fields (see below) so entries merge instead of forking. Auto-approved (writes only to local engagement state). Reaches agents via the master-tools snapshot like `recall`. See "Findings Ledger" below.
- `delegate` (`SpawnAgentTool`) hands a batch of self-contained sub-tasks to isolated agents and **returns immediately** with their ids (`a1`, `a2`, …) — the agents run detached as supervised `asyncio.Task`s so the master keeps its prompt. See `docs/agent-subsystem.md`. The master gets approval REQUIRED on the batch; spawned agents auto-approve within their whitelist. Detachment is master-only (`detached=True`): the **nested** `delegate` an agent receives is built with `detached=False` and blocks on `supervisor.wait(ids=…)` scoped to the ids it spawned. Both collection paths belong to the master — `agent_wait` is registered by the front end and never reaches the master-tools snapshot, and turn-boundary delivery needs a turn — so a detached child would bypass its parent, which would report without its findings while they landed in the master's conversation.
- `delegate`'s per-task `allowed_tools` may only narrow a profile's whitelist, and naming `report` there is tolerated rather than rejected: `ReportTool` is appended by the runner *after* validation and so appears in no profile's list, which made the tool an agent must call to finish the one name that failed the whole batch. `report` alone still fails — it leaves no usable tools.
- Agents carry two handles: an internal `id` (`a1`, monotonic and never reused within its supervisor, what `agent_wait`/logs key on) and a user-facing `name` (`google-pinger`). `delegate` takes an optional `name` per task so the master names it in the same call — no extra LLM round-trip; unnamed tasks fall back to a slug of the instruction, then the profile. Names are slugified and deduped per session; `supervisor.get()` and `wait(ids=…)` resolve either handle. **CLI output prints the name only**; model-facing text carries `name (id, profile)`.
- `agent_wait` (`AgentWaitTool`) is the collection half: it blocks on named (or all outstanding) agents and returns their reports. Auto-approved. A `timeout_s` returns the ready reports plus a `Still running: …` line rather than raising. The safety net for a master that never calls it is **turn-boundary delivery** — each front end drains `supervisor.drain_finished_reports()` before a new turn and appends each undelivered report as a `user` message, exactly once (`AgentSession.report_delivered`). Both paths render through `agents/report_format.py`, so the model sees one shape. A turn boundary needs a turn, so the CLI also *makes* one: `KerkovCLI._wake_on_finished_report` (subscribed to the supervisor) calls `InputManager.wake_chat_prompt()`, which ends an idle chat prompt with `WAKE_SENTINEL`; the run loop answers it with `AgentReportWakeMessage`, a turn carrying the delivered report and no user message. Only a **master-owned** report wakes it (a `top_level` session, `parent_depth==0`) — a nested child reports to its parent's `agent_wait`, so waking the master would run an empty turn; `AgentReportWakeMessage` also re-checks `supervisor.has_undelivered_reports()` before running the engine, in case that `agent_wait` collected it in between. `wake_chat_prompt` only fires on the `wakeable` main chat prompt, never the resume picker that reuses the same session, and is idempotent within one teardown so two reports finishing at once do not clobber the stashed draft. Skipped while attached to an agent (the prompt is that agent's), while a picker or approval box owns stdin, and mid-turn — a mid-turn wake is dropped but not lost, because the run loop re-checks `has_undelivered_reports()` before the next idle prompt. Typed text is stashed and restored like a takeover's.
- **Agents get their own `TokenTracker` + `ContextCompactor`** (`AgentRunner._build_compactor`), targeting the agent's own window (`provider.get_max_context_tokens()`, else `MAX_CONTEXT_TOKENS`). Without one the iteration cap is the only thing between a long run and a provider context-limit error, which surfaces to the master as `stuck` rather than as partial findings (issue #205; it killed four agents in engagement `2026-09-07-0251da77`). The tracker is shared with the `AgentSession`, so `/agents` and `AgentSupervisor.total_agent_tokens()` read it live. Spend is **not** folded into the master's `TokenTracker`: `total_tokens` there is the size of the master's context and drives its compaction, while `cumulative_tokens` is what has been billed. Compaction bills too — the summarizer/rollup call adds to `cumulative_tokens` via `TokenTracker.record_side_spend` without touching `total_tokens` (its prompt is not the conversation size). A terminating `report` breaks the loop *before* the post-turn compaction check, so a summarizer failure can never replace an already-produced report with the `stuck` stub. Spend reaches the model through `AgentRunReport.tokens_used` in the report, and the operator through the `/agents` table. Each batch also runs against a **shallow copy of the provider** (`_pin_model`), because `/model` and `/provider` mutate the one shared instance under in-flight agents.
- `AgentSupervisor` (one per `KerkovCLI`, recreated for each conversation in `WebKerkovSession`) owns the live agents: task handles, ids, the shared workspace, `cancel`/`cancel_all`, and report delivery. `AgentRegistry` stays the budget *policy* (depth/total); the supervisor enforces `AGENT_MAX_CONCURRENT` over live instances, raising the `ConcurrencyExceeded` subclass of `BudgetExceeded` so `delegate` keeps one error path while still telling a full pool (clears itself) from a spent lifetime budget (never does). The advice is the caller's to add: the master is told to collect with `agent_wait`, a nested `delegate` to do the work itself — it has no `agent_wait`, and the agents holding the slots are its own siblings blocked in `_collect` on the same batch. Quit paths (`/q`, `Ctrl-C`, EOF) must `await cancel_all()` or agents are orphaned; a `--message` one-shot instead waits for them, records the reports in the transcript, and prints them, since there is no next turn. CLI conversation switches (`/clear`, `/resume`) go through `settle_agents_for_conversation_switch()` — cancel, then `discard_pending_reports()` — because turn-boundary delivery fires against whatever conversation is live at the next turn, so an in-flight agent's report would otherwise be filed and persisted under a different engagement. CLI `/mode` currently bypasses this cleanup. Web `/clear` and `/mode` use `_reset_agents()` to unsubscribe the old supervisor's callbacks, cancel agents, discard pending reports, and rebuild the supervisor and tool handles before resetting the Agents panel. Web agent ids restart at `a1` for the new conversation; the same `AgentRegistry` is retained, so the lifetime spawn budget does not reset. Every spawned task also carries a done-callback (`_settle_if_unfinished`): a task cancelled before its first event-loop cycle never enters `_supervise`, so the in-loop `CancelledError` handler cannot run and the session would sit in `QUEUED` — active, holding an `AGENT_MAX_CONCURRENT` slot nothing can free.
- The master's `output_sink` is a `BufferingSink` (`cli/buffering_sink.py`) wrapping `ConsoleSink`. `AgentAttachView.attach()` starts buffering and `detach()` replays in order, so master narration never interleaves with an attached agent's output. `status()` is never recorded (a replayed spinner is a stale line) and `start_turn()` passes through so the turn timer stays real. Capped at `MAX_BUFFERED_EVENTS` (oldest dropped, count reported). Anything printed during a turn must go through the sink or it punches through the buffer — `_deliver_agent_reports` and `get_response`'s error path do.
- **Agent focus** (`cli/agent_focus_manager.py`) is the single answer to "which conversation is the terminal pointed at" — the master, or one agent **id** (never a name: a rename would move focus). `/agents` lists active + finished sessions and opens the provider-style picker; `AgentAttachView` (`cli/agent_attach.py`) replays the tail of the focused agent's `QuietSink` buffer and then streams the rest via `supervisor.subscribe`, with a cursor keeping the two from overlapping. `cli/agent_display.py` is the one renderer behind the `/agents` table, the picker rows, the attached prompt prefix, and the strip under the chat prompt (`agent_strip`, supplied to `InputManager` via `set_status_provider`; style/text fragments, never markup, since the model chooses agent names — absent entirely when no agent is active or awaiting delivery, and there is no strip mid-turn because there is no prompt mid-turn). Typed chat while attached is queued on that agent's `inbox` rather than reaching the master (the user is addressing the agent), while slash commands still run so `/back` and `/q` always work. `/clear` and `/resume` detach before settling agents so focus never points into the replaced conversation.
- **Operator input and per-agent stop.** `LoopSession` gained `inbox` (an `Optional[asyncio.Queue[str]]`) and `interrupt_ends_turn`. `_drain_inbox` empties the inbox at the **top of each `run_loop` iteration** — the only site where history is provider-valid for an insert, since every `tool_use` already has its result — and appends each line through `_append` (history *and* the agent's JSONL) behind `OPERATOR_MESSAGE_PREFIX`, so the agent reads it as a live instruction rather than a restatement of its task. Master and web sessions pass no inbox, so both are unchanged. `interrupt_ends_turn` (agents `True`, master `False`) is what makes a cancel terminal: `_handle_tool_calls` otherwise *absorbs* `InterruptedByUser` and continues, which is right for the master's Escape ("stop this tool, keep the turn") and wrong for an agent. Neither branch resets the handle when the flag is set, so `AgentRunner` reads `interrupt_requested.is_set()` afterwards and reports `partial` with what it had instead of `stuck` (a `report` that beat the cancel still wins). A stop landing *between* the calls of one batch is caught before the next call starts: `_handle_tool_calls` re-checks the flag every iteration and answers the remaining `call_id`s with a skip result, because `run_cancellable` schedules the coroutine regardless and a tool that finishes without yielding beats the watcher. `LoopSession.stop_exempt_tools` is the lone exception (`report` only — it writes nothing outside the run and carries the findings the stop was meant to preserve); the master's is empty. `EventInterrupt` (`cli/cancellable_task.py`) is the concrete handle the supervisor sets; `run_cancellable` cancels and awaits its two child tasks when its own caller is cancelled, so a hard cancel takes the in-flight tool down instead of leaving it to land its side effect. `AgentSupervisor.cancel`/`cancel_all` set it and allow `CANCEL_GRACE_SECONDS` (2.0, one window shared across a `cancel_all`) before hard-cancelling; the *synchronous* `request_cancel`/`request_cancel_all` stay hard cancels because their callers (`WebKerkovSession.close()`, a cancelled parent) cannot await a grace window. There is no prompt while the master's turn runs, so a mid-turn `Ctrl-O` attach is watch-only until the turn ends — you type at the next prompt.
- **Operator review of an agent's tool calls.** Agents auto-approve inside their whitelist; `/agents review <name|id> [on|off]` opts one out of that, and only while the operator is **attached to it** (`AttachedAgentReview.should_review`: `session.review_tools` on, that agent focused, and the run interactive). A detached agent has nobody to answer and would simply hang; only one agent is on screen, so two can never compete for one answer. `SupervisedAgentApproval` (`agents/agent_approval.py`) is the strategy every runner is built with — it auto-approves when its `AgentReviewGate` declines, otherwise marks the session `BLOCKED_ON_INPUT` (the first stage to reach that state) and defers to the master's own `ToolApprovalCliHelper`, so `/approval` modes and allow/deny rules apply unchanged (`report({})` is already auto-allowed, so review never blocks an agent finishing). The gate lives in the CLI because "is this agent on screen" is a terminal question. Getting the box onto the screen needs `InputManager.takeover()`: `_terminal_free` is an event cleared by both the picker and a takeover so they wait for each other; a live chat prompt is exited with `TAKEOVER_SENTINEL` (its typed text stashed and restored) and `get_line` swallows that and re-prompts; `start_watching_for_interrupt` is inert during a takeover; and `ToolApprovalCliHelper` holds an `asyncio.Lock` around the box because the master's turn and an attached agent prompt through the same transient prompt_toolkit session.
- **Finding an agent run afterwards.** `/agents` only knows this process — its sessions die with the CLI — so discovery has a disk half. `EngagementStore.list_engagements` takes an optional `kind`, applied *before* the limit (filtering after it let a directory of agent runs push every conversation out of a ten-row table); `/engagements` lists conversations, `/engagements agents` lists sub-runs with parent linkage and task, and the `/resume` picker offers conversations only. `/resume <agent-engagement-id>` opens that run **read-only** (`cli/agent_transcript.py`) instead of restoring it — an agent engagement's `mode="agent"` is not a `ModeType`, and continuing one would detach it from the `report` its parent is waiting on.
- **Master and all agents in a tree share one run workspace**, keyed on the *root* engagement id (same rule as the KB store) and injected into every `AgentRunner` by the supervisor — a per-agent directory would be invisible to the master and to siblings. Tradeoff: concurrent agents can clobber files by name; the mitigation is a prompt convention to namespace outputs, not enforced isolation.

## Providers

Seven providers listed in `SUPPORTED_PROVIDERS` (`src/kerkov/providers/__init__.py`) and constructed by `create_provider_from_name` there; `ProviderManager` (`provider_manager.py`) owns initialization and runtime switching:
`anthropic` (alias `claude`), `gemini` (aliases `google`, `google-gemini`), `nvidia` (aliases `nim`, `nvidia-nim`), `openrouter` (alias `open-router`), `deepseek`, `ollama`, `codex` (alias `openai-codex`). Codex auth is OAuth-based and starts automatically when Codex is selected through provider setup; tokens are persisted in `data/providers/codex/auth.json`. Other providers resolve their API key from config or the `CredentialManager`, which can prompt interactively and save to keyring/local file.

Successful interactive provider selections persist the canonical provider name as `LLM_PROVIDER` in `~/.kerkov/settings.json` (path override: `KERKOV_SETTINGS_FILE`). Explicit environment and `.env` values take precedence, followed by saved settings and built-in defaults. Credentials remain separate. Missing Codex sign-in at startup enters setup quietly, like a missing API key.

The web picker uses `web/runtime/providers.py` for guarded session switches and `web/runtime/provider_history.py` to prepare history before smaller-context switches. Provider replay normalization lives in `providers/replay.py`; bounded background SDK workers live in `providers/workers.py`. CLI startup/setup uses inexpensive `validate_connection` checks. Web model selection uses `validate_model`: NVIDIA probes selected-model inference and Ollama checks completion capabilities (falling back to a minimal chat probe on older servers). Validation and metadata each have a 20-second budget; history preparation has a separate 180-second budget and identifies failures of the current summarizing provider.

## Modes & Autonomy

Modes (`src/kerkov/cli/modes.py`): `RECON`, `AUDIT` (default), `OFFENSIVE`, `CTF`. The `--mode` CLI flag exposes only recon/audit/offensive; CTF is selectable at runtime via `/mode ctf`.

Autonomy levels (`src/kerkov/cli/autonomy_manager.py`): `1 GUIDED`, `2 STANDARD` (default), `3 AGGRESSIVE`, `4 AUTONOMOUS`. Level 4 requires `ALLOW_AUTONOMOUS=true`.

Autonomy presets two independent axes, each overridable on its own:
- Verbosity (`verbosity_manager.py`, `/verbosity`, `--verbosity`): `guided`, `standard`, `aggressive`, `silent`.
- Approval gating (`approval_mode_manager.py` + `approval_rules.py`, `/approval`, `--approval`): `strict`, `normal`, `permissive`, `yolo`. `/yolo` and `--yolo` are sugar for `yolo`. Rules load from `config/approvals.yaml`, overridable per-user at `~/.kerkov/approvals.yaml`.

## Slash Commands

Registered in `src/kerkov/cli/input_parser.py`: `/help`, `/prompt`, `/clear`, `/q` (`quit`, `exit`), `/mode`, `/autonomy`, `/verbosity`, `/approval`, `/yolo`, `/provider` (`/providers`), `/model` (`/models`), `/skill [search <q>|<id> [args]]`, `/agents [name|id|master] | /agents stop <name|id> | /agents review <name|id> [on|off]`, `/back`, `/engagements [agents]`, `/resume [id]`, `/auth` (`/credentials`), `/logout` (`/signout`), `/zap [status|stop]`, `/searxng [setup|start|stop|status]`. Each maps to a handler under `src/kerkov/cli/messages/`. `Ctrl-O` is a keybinding for `/agents`; the text already typed is stashed and restored as the next prompt's default. It works at the chat prompt (a prompt_toolkit binding — chat prompt only, since on a credential or approval prompt it would be read as the answer) **and mid-turn** (the cbreak watcher in `input_manager` sets `switcher_requested`, which `KerkovCLI._watch_for_switcher` awaits for the duration of `run_loop`; POSIX TTY only). Mid-turn, `begin_switcher`/`end_switcher` keep `start_watching_for_interrupt` inert while the picker owns stdin — a tool call finishing underneath it would otherwise start a second cbreak reader on the same fd and wedge the terminal. A key pressed between awaits is dropped: nothing owns stdin there (pre-existing, applies to Escape too).

## Managed SearXNG (`/searxng`)

`SearxngBackend` needs an instance that answers `?format=json`, and a stock SearXNG does not: the shipped `search.formats` is `[html]` alone, so every request Kerkov makes comes back **403**. `/searxng setup` is the whole fix — it writes `~/.kerkov/searxng/settings.yml` with `json` added, a generated `server.secret_key` and `limiter: false` (httpx is not a browser, so bot detection would block Kerkov), pulls `docker.io/searxng/searxng:latest`, publishes it on a free loopback port and then verifies with a real `format=json` probe before persisting `SEARCH_PROVIDER`/`SEARCH_BASE_URL` through `save_user_setting` (both were added to `SUPPORTED_USER_SETTINGS`).

`DockerSearxngRuntime` (`core/websearch/searxng_runtime.py`) owns the Docker half, mirroring `DockerZapRuntime`: preflight, pull, labeled `docker run -d`, managed-label guard on the container name, `stop`, log tail. The generic subprocess plumbing both runtimes share — `CommandResult`/`CommandRunner`/`SubprocessCommandRunner` plus the Docker preflight diagnosis — was lifted out of `zap_runtime` into `core/docker_command.py`; `docker_preflight_failure` takes the caller's `action` so each runtime names its own operation in the error.

The settings file is mounted **read-only at `/etc/searxng/settings.yml`** and written `0644` inside a `0700` directory: the container drops to uid 977 and reads it through the bind mount, so owner-only bits would make it unreadable, while the private parent keeps it away from other host users. `FORCE_OWNERSHIP=false` is passed because the upstream entrypoint otherwise warns about a mount it cannot chown. Lifecycle asymmetry vs ZAP: **`/searxng stop` keeps `SEARCH_BASE_URL`** — it is the port `/searxng start` brings the same instance back on — and clears only `SEARCH_PROVIDER` so `web_search` is not left pointed at a dead instance. `/searxng start` runs readiness and JSON-API verification **even when it finds the container already up**: a start whose probe failed leaves the container running with `SEARCH_PROVIDER` unsaved, so the retry meant to finish it has to re-probe rather than just report the container as running. `provision()` writes through a `tempfile.mkstemp` file rather than a fixed `settings.yml.tmp`, because `prepare_private_parent` leaves an existing config directory's permissions alone and a predictable temp name in a shared directory is plantable as a symlink. Container removal passes `--volumes` — the image declares VOLUMEs for its config and cache directories and Kerkov binds only the settings file, so each run creates anonymous volumes that a plain `docker rm --force` would orphan. `setup`/`start` reload search tools after saving settings, and `stop` reloads them after clearing the provider. `KerkovCLI.reload_tools()` rebuilds only search tools through `ToolSuite.get_search_tools()`, preserving stateful tools and updating the shared pool used by future agents, including nested delegates. Running agents retain their current tools; the CLI can use the new search backend immediately without a restart.

## Engagements

Conversations persist as JSONL under `~/.kerkov/engagements/`. Resume with `kerkov --continue` (latest) or `kerkov --resume <id>`. `EngagementStore` handles serialization (including provider-specific raw content blocks).

## Knowledge Base (`recall`)

Alongside the JSONL, each engagement gets a SQLite/FTS5 artifact store at `~/.kerkov/engagements/<root_engagement_id>.kb.sqlite`, created lazily on first write. `ConversationEngine` indexes the original tool output before normalizing it for history. Results above `KB_CLIP_THRESHOLD_BYTES` gain an `artifact#N` reference and have oversized metadata values elided (`build_clipped_metadata`). This threshold counts output *and* metadata (`history_footprint_bytes`), since `format_tool_result` renders both and `HTTPTool` includes a parsed copy of the response body in metadata. Clipped stored output also gains an artifact reference when below the KB threshold. Small results are still indexed.

Tool output normalization runs in the shared engine for CLI, web sessions, and agents, including when the KB is disabled or ingestion fails; the output sink receives the original result. Engagement JSONL stores the normalized result. If the KB is disabled or ingestion fails, omitted raw output is not saved in that transcript and cannot be recovered from it. Successful KB ingestion stores the full raw output for `recall`. Bulky metadata values are also elided when output normalization changes the body or the combined output/metadata character count exceeds the output limit, preventing an embedded copy of the body from bypassing normalization. Output at or below `TOOL_OUTPUT_MAX_CHARS` (6000) stays unchanged. Larger output first collapses runs of at least three consecutive identical lines, ignoring trailing spaces and tabs when comparing them and only replacing a run when it saves space. If the collapsed text still exceeds the limit, the preview retains `TOOL_OUTPUT_HEAD_CHARS` (1500) and `TOOL_OUTPUT_TAIL_CHARS` (500), proportionally reducing that split when its sum exceeds the limit. Changed output carries the original character count; annotations and artifact references are outside the retained-content limit. The maximum must be positive, the head/tail counts nonnegative, and at least one side must retain a character. `recall` is exempt so explicitly expanding a stored artifact can return the full raw output.

`read_url` pages are indexed and retain their artifact references, but `KB_CLIP_EXEMPT_TOOLS` keeps them inline under their own `READ_MAX_CHARS` budget, including when the KB is disabled or ingestion fails. A second normalization or knowledge-base preview would preserve paging metadata while hiding part of the requested head before `next_offset`; continuing without `recall` would skip that hidden text. Stored artifact references still let later context compaction evict these pages while keeping them recoverable through `recall`.

`recall(source=...)` is a substring matched against both the producing tool name and the artifact title, which is where the target lands (`http: <url>`, `read: <path>`) — the source column itself only ever holds the tool name, so a host or URL filter would otherwise silently return nothing.

Artifacts are classified by `ArtifactKind` (`core/knowledge_base/models.py`), assigned from the producing tool by `artifact_kind_for_tool`: `read` → `FILE`, `http` → `HTTP_RESPONSE`, everything else → `TOOL_OUTPUT`. Only kinds something can actually produce are members — an unreachable value in the enum becomes a `recall(kind=...)` filter that returns confidently empty results forever. `credential` and `note` are deliberately absent from `ArtifactKind`; those facts live in the findings ledger (see below) as its own sections, not as artifact kinds.

**One store per engagement *tree*, not per engagement id.** A spawned agent gets its own `engagement_id`, so keying the file on that id would give each agent a private database its master could never read. Instead `engagement_id` is a *column*, the file is named for the root, and `SpawnAgentTool` passes the master's `EngagementKnowledgeBase` down to `AgentRunner` rather than letting agents open their own. `recall` searches the whole tree by default and takes an optional `engagement` filter — which is how the master drills into the raw output behind a delegated agent's summarized FINDINGS, using the id the report formatter prints next to them.

Resolving which store an engagement belongs to walks `parent_engagement_id` to the root (`resolve_root_engagement_id`). Note the current spawn wiring hands nested spawn tools the *master's* store, so every agent records the master as its parent regardless of depth and the walk resolves in one hop; it is written as a bounded loop so a later fix to that parentage keeps working. `delete_engagement` deletes the `.kb.sqlite` only for a root — deleting an agent sub-run drops just its rows, since the file belongs to its master.

The store is plaintext on local disk and holds whatever the tools returned, harvested credentials included. Nothing is redacted and nothing leaves the machine.

## Findings Ledger (`ledger`)

A structured store of resources and confirmed facts (`assets / targets / connections / hosts / services / credentials / findings / flags / next_steps`) that the model writes to via the `ledger` tool and that is **re-injected every turn**, so it survives context compaction verbatim — the fix for "forgot the credential found 40 messages ago". It lives in the **same `.kb.sqlite`** as `recall` (table `ledger_entries`, added in schema v2; an existing v1 DB migrates in place, keeping its artifacts), so it inherits the KB's root-keying, WAL/`busy_timeout` concurrency, and lifecycle. `EngagementKnowledgeBase` owns the SQL; `FindingsLedger` (`core/knowledge_base/findings_ledger.py`) owns the domain logic — per-section dedup identity, merge-on-conflict (new detail enriches a row rather than duplicating it), and a compact, byte-stable serialization cached on `ledger_revision()`.

Identity is required, not guessed: `identity_error()` rejects an `add` that cannot be identified (hosts need ip-or-hostname, services host+port, credentials username plus host-or-source, findings a title, flags a value, next_steps a step) because a hash-fallback row never merges with its own later enrichment, and host-less services would all collapse onto the same port. Identity still firms up over time, so `_identity()` also returns *alias* keys (the hostname a host was first known by, the `source` before a `host`, the credential recorded before its `kind`); `add_ledger_entry` looks rows up under key-or-alias, folds duplicates into the oldest row and promotes it to the canonical key. For ordinary fact merges, the first contributor keeps `engagement_id` ownership — `delete_engagement_ledger_rows` deletes by owner, so reassigning it would let an enriching agent's cleanup take the master's facts. An explicit new `artifact_ref` replaces earlier evidence; a later detail-only add preserves the existing link. Connections use the typed assertion rules below instead of the generic merge contract.

Connections assert `resolves_to` (domain → IP), `deploys_to` (repository → URL/domain/IP), or direct `reaches` (domain/IP or explicit vantage → domain/IP). Resource endpoints use existing asset/target ledger IDs. `observed` requires an existing `artifact_ref`; `declared` requires a note and may carry an existing artifact reference. Writes validate endpoints and evidence in one transaction, belong to the root engagement, and deduplicate by canonical source/relation/target across asset/target roles, plus protocol and port for `reaches`. A fresh observation replaces assertion metadata and evidence together; older reachability observations return `stale_observation_retained`; a later declaration preserves an existing observation and its evidence, and the tool reports that the declaration and its note were not stored (`outcome=observation_retained`). Remove the connection first to retract that observation intentionally. Name or role edits preserve connections; identity edits and removal redirect them to a remaining role of the same resource, or retire them when none remains. Deleting artifact-producing agent rows (`delete_engagement_rows`) also deletes observations using those artifacts even though the connection rows are root-owned, while declarations survive with their evidence link cleared. `op=graph` exposes the inventory and connections as JSON pages capped at 5,000 characters, with `offset`/`next_offset` continuation (nodes before edges; restart after edits). Oversized resource text is explicitly omitted via `omitted_fields`, while ledger IDs remain usable. These pages bypass generic history clipping; `FindingsLedger.graph()` provides the structured projection, including derived `uses_host` edges only for exact URL-host matches. DNS and deployment relationships are never inferred.

The model-facing tool exposes `op=add|list|remove|graph`; assets and targets additionally support the web edit path described below. Injection is transient: `ConversationEngine` re-serializes the ledger at the top of each loop iteration into `LoopSession.ledger_block` and `_messages_for_provider` inserts it as a `system` message. Placement is provider-dependent for prompt-cache safety: providers that cache a stable prompt prefix (`BaseLLMProvider.caches_prompt_prefix`, currently Anthropic and DeepSeek) get the ledger at the **tail** (final message, after stable history and any Anthropic cache breakpoint) so a ledger update never invalidates the cached system+tools+history prefix — trading head-position salience for recency salience; every other provider keeps it high, right after the base prompt. It is never written into `history`, so `ContextCompactor` never sees it — no exclusion code needed. Because the block is outside compaction it cannot be reclaimed once it grows, so `serialize()` trims to `max_injected_bytes` (`DEFAULT_MAX_INJECTED_BYTES`, 16000 ≈ 4k tokens) dropping whole-section-priority-last first (`_SECTION_PRIORITY`: credentials/flags/findings survive host and service enumeration) and appends a count of what it omitted; nothing is deleted, `ledger op=list` still reads everything. With a ledger actually open, the compaction prompt is softened (`ledger_active` flag) to lean on narrative/attack-chain reasoning rather than exhaustively re-listing creds/IPs/flags, while still keeping anything not obviously a ledger fact — the flag tracks the live `FindingsLedger`, not `KB_ENABLED`, since a store that failed to open would otherwise license the summarizer to drop the only copy.

Both front ends wire it: `KerkovCLI` and `WebKerkovSession` each build the `FindingsLedger` beside the knowledge base, register `LedgerTool` under `KB_ENABLED`, and pass `ledger=` into their `LoopSession` — the mode prompt instructs the model to record facts, so a front end without the tool would be advertising something it does not have.

**Web inventory.** `WebInventory` (`web/runtime/inventory.py`) handles `inventory.list`, `inventory.save`, and `inventory.evidence` over the browser session's WebSocket. It exposes assets and targets plus an inventory.snapshot graph from project_resource_graph, sharing the ledger with the CLI and agents. The graph projects connection rows with notes and artifact references from the same filtered read; credentials and flags remain excluded. A first save initializes the engagement and KB without a configured provider; saves serialize against conversation work. Resource roles are context, not tool permissions. `Resource` validates domains, IP addresses, HTTP(S) URLs, and absolute repository paths, with an optional name; `RESOURCE_SECTIONS` in `core/knowledge_base/models.py` defines the resource roles used by the ledger, store, and web adapter. Resource rows always belong to the root engagement, including agent writes.

`FindingsLedger.save_resource` normalizes the payload and calls `EngagementKnowledgeBase.save_resource_entry`, which uses one SQLite transaction to add, edit, move between roles, or fold duplicate identities. `expected_updated_at` rejects a stale edit of the selected row. An edit without a different destination replaces its fields, so an omitted name clears it; an add or edit into another existing row merges nonempty supplied fields with the destination's latest stored fields and preserves omitted ones. A fold keeps the destination row ID and removes the original. Evidence belongs to resource identity: a destination's existing reference wins, the old reference can follow an unchanged identity across a role move, and changing identity never carries unrelated old evidence forward. Evidence requests fetch only the selected resource's linked artifact, recheck its revision after reading, and return at most 32,000 body characters.

Connections also support direct `reaches` assertions from domain/IP resources or explicit vantage labels. Reachability identity includes source, target, protocol and port. Observations default to the evidence artifact creation time and cannot postdate it; `stale_observation_retained` preserves newer evidence when an older observation arrives. IP addresses and existing domains must use `source_id`. Record routes when the source matters rather than duplicating every service.

**Engagement retirement ordering.** Web `/clear` and `/mode` await `_retire_engagement`: detach the old KB, ledger, and workspace from the session and reset the inventory context token immediately; then `_reset_agents` settles agents and pending reports and `inventory.settle` drains in-flight inventory requests; only then close the detached KB. This keeps old responses out of the new inventory and avoids closing storage while an old request still uses it. The synchronous disconnect `close()` instead cancels work and closes storage; the browser retains its last inventory snapshot read-only.

Tree-shared like the KB: spawned agents both write to and receive the injected ledger. The `ledger` tool reaches agents via the master-tools snapshot; because tools pass by reference, an agent's writes are recorded under the master's `engagement_id` (cosmetic — still tree-shared and recalled). Gated on the same `KB_ENABLED` (no separate flag) and auto-approved in `config/approvals.yaml` — and in its packaged twin `src/kerkov/config/approvals.yaml`, which `default_approvals_source` falls back to outside a source checkout, so the two must be kept in step. Secrets are stored and re-injected **unmasked** — same cleartext/local-only/no-telemetry posture as the KB. `delete_engagement` drops an agent sub-run's ledger rows (`delete_engagement_ledger_rows`) and takes the whole file with a root delete.

## Compaction

`ContextCompactor` runs when `TokenTracker.total_tokens` crosses `COMPACTION_THRESHOLD_PCT` of `MAX_CONTEXT_TOKENS` — reactive to authoritative `response.usage` only; there is deliberately **no local byte/char token estimator**. One compaction goes in a fixed order: **evict large tool results → summarize the remaining narrative → roll summaries up** once the block outgrows its cap.

`Message` carries two persisted provenance fields (`models/basic_models.py`, threaded through `EngagementEntry` and both `EngagementStore` write paths plus `load_engagement`). Persistence is the whole point: `_check_compaction` calls `override_engagement_messages`, which **rewrites the JSONL with the compacted history** — the pre-compaction transcript is gone from disk — and a mark that lived only in memory would be dropped on `/resume`, so the next compaction would re-summarize summaries again with every in-memory test still green.

- `summary_level` — `None` for ordinary messages, `1` for a compaction summary, `2` for a rolled-up one. `select_messages_to_compact()` advances `start` past the leading summary block, so a summary is never fed back through `build_summarization_prompt()` as fresh narrative. Summaries stay contiguous at the head by construction: each new one is inserted *after* those already there, and a rollup replaces a run of level-1s in place, so the block is always level-2s then level-1s.
- `artifact_ref` — the knowledge-base artifact behind a `role="tool"` message. `_ingest_and_clip` returns it alongside the history result and stamps it **whether or not the result was clipped**; a sub-threshold result has an artifact too, and that is the case eviction exists to exploit. The alternative — looking the artifact up at compaction time — would need a KB index on `call_id`, which is buried in the artifact's metadata JSON and neither indexed nor queryable.

Selection (`select_messages_to_compact`) keeps the system prompt, the summary block and a recent window, and it fails **loudly**: a `None` return logs, and `_check_compaction` warns once (`compaction_stalled_warning_shown`, reset by the next successful compaction) rather than treating a falsy return as a no-op success — the engine used to ask for compaction, get nothing and say nothing, every turn. The recent window is measured by `preserve_boundary()`, which preserves `PRESERVE_RECENT_TURNS` (6) messages **subject to `PRESERVE_RECENT_BYTES`** (65536): count alone exempted the newest messages whatever their size, so one oversized result — a `recall(full=true)` expansion, deliberately not clipped on the way into history — pinned the window for six messages with eviction structurally forbidden to touch it. The budget counts serialized UTF-8 `content` and `raw_blocks`, including both SDK block models and persisted dictionaries; tool-call arguments and reasoning therefore count even when `content` is empty. Selection applies that budget even to histories with seven or fewer messages. If exhausting the budget leaves the boundary inside a completed tool exchange, it advances past the results so keeping the pair intact cannot pin the oversized payload. The newest message and its associated tool exchange are always preserved regardless of cost, because compaction runs directly after `_handle_tool_calls` appends the results it would otherwise drop, and answering the model's own call with a summary of it is worse than one more turn over threshold. The end boundary is then walked back out of a trailing tool-result run so a `tool_use`/`tool_result` group is never split; when that walk-back consumes the whole range, `_forward_group_boundary()` walks *forward* past the run instead of giving up — the group stays intact from the other side. A run reaching the end of history has no forward boundary (anything preserved after it would be a `tool_result` whose `tool_use` was compacted away, which providers reject), so that exchange must stay intact; selection returns `None` when no earlier messages are eligible either.

Eviction (`evict_tool_results`) rewrites a *copy* of the selected range before summarizing, and replaces **only the output body** — `split_tool_output` cuts at `TOOL_OUTPUT_MARKER`, which is why `format_tool_result` renders output last. The header it leaves standing carries the tool name, status, error and metadata, which live *only* in the conversation message: the artifact behind it holds `ToolResult.output` alone, so collapsing the whole message would destroy them with no way to recall them back. The floor (`EVICT_TOOL_RESULT_MIN_BYTES`) is measured against that body for the same reason — a metadata-heavy result with a short output has nothing worth evicting. The body becomes `build_evicted_tool_reference` (bare `artifact#N` handle) or, with no artifact — KB off, or ingestion failed — `build_evicted_tool_clip` (head/tail, unrecoverable). Every candidate over the floor is evicted, so there is no largest-first ordering: the floor, not a byte budget, is the cutoff. The reference builders live in `core/tool_output.py` rather than beside either caller because `conversation_engine` already imports `ContextCompactor` — importing back the other way is a cycle.

Handles are carried **deterministically**, not by prompt alone. The replacement history is built from model-generated text, so an omitted `artifact#N` would be the last copy of it — the messages holding it are dropped in the same step. `collect_artifact_refs()` gathers every id in the range (stamped `artifact_ref` plus any written inline) and `build_artifact_index()` appends them to the summary verbatim; rollup does the same over the summaries it merges, so handles survive every level. The prompts still ask for them in place, next to what they were — the index is the floor, not the intended form. It is capped at `MAX_INDEXED_ARTIFACTS` (60, newest kept) because it rides outside compaction like the summaries.

Rollup runs two bounded passes, both through `build_rollup_prompt()`, which asks for a *merge*, not a further compression. First the level-1 run merges into one level-2 when the block exceeds `MAX_SUMMARIES_BEFORE_ROLLUP` (4); then the level-2s merge among themselves once they exceed `MAX_ROLLED_UP_SUMMARIES` (4). The second pass is what bounds the block, and it is not optional: the summary block is excluded from every compactable range, so "level 2 is never rolled up again" means a long engagement gains a level-2 every couple of compactions until it crosses the context threshold with nothing left to compact. Detail at the head therefore decays more than once — the merge prompt keeps that as slow as it can, and the findings ledger holds the facts losslessly outside compaction either way. This is still a bounded cap rather than the general hierarchy #152 describes.

## Testing
